## 0. Головне

1. **Клієнт тонкий.** Він не містить жодної формули шкоди, влучання, ШІ чи нагород. Клієнт лише:
   - збирає вибір гравця (дія, ціль, hit% зі смуги таймінгу);
   - програє серверний «сценарій ходу» (1028) анімаціями;
   - показує результат (1032).
2. **Мережевий шар — той самий код Gamevil, що в SP.** `e.java` збігається з SP `u.java` рядок у рядок, включно з невикористаним масивом `{0,1,117,126}`. Збігаються кадр, little-endian, рядки фіксованої довжини з нулями та схема «відповідь = opcode+1 + status».
3. **Персонаж походить із SP-бекапу (опкод 256).** На це вказують:
   - коди навичок 3..13 = SP `as.gG` (as.java:84-86);
   - атрибути «база (+бонус)» у порядку Hp/Mp/Atk/Def = SP `{o,q,m,n}+{u,v,s,t}`;
   - тип героя (обличчя) і тип зброї.
4. **Для порту.** Усе, що «знає» клієнт, переноситься 1:1: UI, стан-машина, анімаційні таблиці, SP2, смуга таймінгу. Усе, що «знав» сервер, доведеться вигадувати: бойова математика, CPU, місії, ранги, нагороди.

## 2. Мережевий протокол

### 2.1 Транспорт і кадр

**Адреса.**
- `socket://GAMEVIL_SERVER:GAMEVIL_PORT` береться з маніфесту: `ur.gamevil.net:28200`, версія `GAMEVIL_GAME_VER="0111"` (`g:305-308`).
- Запасні значення `64.14.246.182`, `28200`, `"0111"` вмикаються лише якщо читання властивостей кидає виняток (`g:310-315`).
- Підключення: окремий потік `h` (`h:68-82`). Після `connect` викликається `g.l()`.

**Приймання** (`h:88-119`, `d:30-48`, `k.java`):
- Кадр: `[u16 LE totalLen (разом із цими 2 Б)] [payload totalLen−2]`.
- Довжина читається через `read(c,0,2)`, а **не** `readFully` (`d:34`) — теоретичний баг при фрагментації.
- `h.a = u16 LE opcode` береться з перших двох байтів payload (`h:93`), після чого викликається `g.a(k)` (`g:1888`).
- Обробник ще раз читає `s = k.b()` (opcode) і `by = k.a()` (status, **signed byte**) (`g:1908-1910`).
- Після кожного прийнятого пакета потік спить 100 мс (`h:115-117`), тобто клієнт обробляє не більше ~10 пакетів/с.

**Надсилання** (`e:38-95`, `h:131-163`, `g.c(int)` `g:1609-1704`):
- Структура: `[u16 LE totalLen][u16 LE opcode][поля]`. Status-байта в запиті **немає**.
- Числа — LE: `e.a(int)` дає u16, `e.b(int)` — s32. Рядки `e.a(String,n)` — ASCII, доповнені нулями до n.
- Читання (`k.java`): `a()` s8, `b()` **signed** s16 LE, `c()` s32 LE, `a(n)` — рядок до першого `\0` із `trim()`.
- Debug-друк `SEND DATA` / `RECV DATA` (`d:38-44`, `e:81-87`).

**Порівняння з SP Gamevil Live** (03 §5.1):
- **Обгортка та сама:** `u.java` ≡ `e.java`, відповідь = opcode+1 + status, LE, фіксовані рядки.
- **Відмінності:**
  - порт (SP 28230 у зламаній збірці, MP 28200);
  - рядок версії (SP `"1501"`, MP `"0111"`);
  - логін (SP 530, MP 278/262).
- **Номери перетинаються з іншим змістом:** 256, 258, 262, 512, 768. Отже, це той самий фреймворк, але окремий процес чи гра на сервері [high].
- Код `-49` в обох означає «недопустимий ID чи ім'я» → спільна серверна бібліотека [medium].

### 2.2 Службові механізми

**Keepalive.**
- `h.h` збільшується щокадру (`g:487-500`) і обнуляється на кожному прийомі (`h:95`) та надсиланні (`h:160`).
- Після 100 кадрів тиші клієнт шле **39327 (0x999F)** без тіла і збільшує `dZ`.
- `dZ > 20` → помилка 13 («Your time has expired»).
- `dZ=0` при **будь-якому натисканні клавіші** (`g:2662`). Тобто без натискань сесія живе приблизно 21 × 100 кадрів ≈ 3–4,5 хв.

**Правило 45 с.**
- Якщо між двома надсиланнями минуло понад 45 с, наступне надсилання не відбувається: з'являється помилка 13 і розрив (`g:1613-1620`).
- На практиці keepalive не дає цьому статися.

**Очікування в бою** (`S()` `g:5334-5349`).
- Тайм-аут 80 с ніколи не спрацьовує через баг: рахується `(v − now)`, а це від'ємне число [high].

**Дубль-логін.**
- Пакет з opcode **280** у будь-якому стані означає помилку 17 (`g:1898-1904`).

**Пауза.**
- Якщо застосунок призупинено (`J`) або `H==1` і приходить будь-який пакет, клієнт показує помилку 7 і розриває з'єднання (`g:1890-1897`).

**Вимога до сервера.**
- Кожен вхідний пакет мусить мати щонайменше `opcode + 1 байт`, інакше `k.a()` кидає виняток → `g(3)` → помилка 7.
- Невідомі opcode просто ігноруються.

### 6.2 (b) Справжній онлайн PvP і кооператив

**Архітектура:**
- Python `asyncio` + `websockets` (WSS обов'язково: сторінку pygbag віддають через https).
- SQLite або Postgres.
- Сервер авторитарний: той самий резолвер, що в A5/A6, тільки на сервері.

**Клієнт у браузері:**
- сирих сокетів у pygbag немає, лише WebSocket через JS-interop/aio;
- API треба перевірити окремим спайком **[medium]**.

**Чи зберігати оригінальний бінарний протокол?**
- Переваги:
  - схема повідомлень уже повністю задокументована;
  - компактний;
  - **сумісність з оригінальним JAR**: в емуляторах (J2ME Loader, KEmulator, FreeJ2ME) досить змінити `GAMEVIL_SERVER/PORT` у маніфесті — DRM неактивний;
  - сервер може **дописувати поля в кінець** пакетів, бо оригінальний клієнт ігнорує зайві байти (наприклад, 1026 читає лише status).
- Недоліки:
  - лише ASCII з фіксованою довжиною;
  - gold/fame/exp у s16;
  - немає токена сесії, 262 без пароля;
  - hit% повідомляє клієнт;
  - пастки: ≤3 рядки в 1294, `aT ≤ 4`, face 0..3, монстр без навичок, порядок 513 → 514.
- Рекомендація:
  - внутрішньо — dataclass-повідомлення з тими ж opcode-іменами;
  - кодеки: (1) оригінальний бінарний — для опційного TCP:28200-шлюзу й навіть для WS-binary; (2) за бажанням JSON для налагодження;
  - для нових клієнтів додати автентифікацію токеном.

**Античит:**
- Резолюцію вже рахує сервер — оригінальна архітектура тут правильна.
- hit%:
  - сервер сам обирає `cz` і передає його в 1026 (дописаним полем);
  - приймає лише значення з множини `{20+k·cz} ∪ {100}`;
  - перевіряє правдоподібність часу між 1026 і 1027 з урахуванням швидкості та латентності (грубо).
- Допуск навички за MP перевіряє сервер.
- **Завантаження персонажа з SP:** сейв SP-порту локальний, тобто його можна редагувати. Варіанти:
  - валідувати стати за SP-правилами: +3 очки за рівень, HP +5, MP +3, ATK/DEF +1 за очко, бонуси предметів у межах таблиць `kibo/sungbo/shinki` з 03;
  - або вести окрему серверну прогресію.
- Також: rate-limit, розміри полів, захист від дубль-логіну (280).
